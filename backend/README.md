# Divra API

NestJS 12 + Drizzle (PostgreSQL). Вход по подписи кошелька Solana, JWT-доступ, refresh-токены с ротацией.

## Запуск

```bash
cp .env.example .env              # и сгенерируй JWT_SECRET: openssl rand -base64 48
docker compose up -d              # PostgreSQL на 127.0.0.1:5432 (или свой: createdb divra)
npm install
npm run db:migrate
npm run start:dev                 # http://localhost:3000/api
```

Посмотреть базу — Drizzle Studio (адрес берёт из `.env`, схему — из `src/database/schema`):

```bash
npm run db:studio                 # https://local.drizzle.studio
```

Фронтенд в dev ходит сюда через прокси Vite (`/api` → `localhost:3000`), поэтому для браузера это один origin.

## API

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| POST | `/api/auth/wallet/challenge` | публичный | Вызов на подпись: memo-транзакция с доменом, адресом, nonce и сроком |
| POST | `/api/auth/wallet/verify` | публичный | Проверка подписи → регистрация/вход, access-токен в ответе, refresh — в cookie |
| POST | `/api/auth/refresh` | cookie | Ротация refresh-токена, новый access-токен |
| POST | `/api/auth/sign-out` | cookie | Отзыв refresh-токена этого устройства |
| GET | `/api/me` | Bearer JWT | Профиль и кошельки |
| GET | `/api/me/overview` | Bearer JWT | Главная: итог «тебе должны / ты должен», группы с балансом, последние расходы |
| POST | `/api/groups` | Bearer JWT | Новая группа, создатель — первый участник |
| GET | `/api/groups/:id/overview` | участник группы | Участники, баланс, долги, расходы |
| POST | `/api/groups/:id/members` | участник группы | Участник по имени, без кошелька (pending) |
| POST | `/api/groups/:id/expenses` | участник группы | Расход: плательщик, доли, исходная валюта и курс |
| POST | `/api/groups/:id/invites` | участник группы | Ссылка-приглашение: общая или персональная (`claimMemberId`) |
| GET | `/api/invites/:code` | публичный | Превью приглашения до входа |
| POST | `/api/invites/:code/accept` | Bearer JWT | Вступить в группу по ссылке |
| POST | `/api/groups/:id/payment-requests` | участник группы | Запросить долг: ссылка Solana Pay на каждого должника |
| GET | `/api/groups/:id/payment-requests` | участник группы | Мои запросы в группе: статус (ждёт / оплачен / истёк), ссылка, QR; последние 50 |
| POST | `/api/groups/:id/settlements` | участник группы | «Рассчитаться»: собрать одну транзакцию с переводами выбранным |
| POST | `/api/groups/:id/settlements/:sid/submit` | тот, кто собрал | Отправить подписанную транзакцию, дождаться и сверить в сети |
| GET | `/api/wallets/:address/balances` | Bearer JWT, свой кошелёк | Балансы USDC/USDT |
| GET | `/api/payment-requests/:code` | публичный | Страница запроса для того, кто платит; заодно ищет оплату в сети |
| POST | `/api/payment-requests/:code/transaction` | публичный, только с фронтенда | Собрать перевод для кошелька плательщика (`{ account }`) |
| POST | `/api/payment-requests/:code/submit` | публичный, только с фронтенда | Отправить подписанный перевод в сеть |
| GET | `/api/health` | публичный | Проверка живости |

Всё, что не помечено `@Public()`, требует `Authorization: Bearer <access-token>` — guard `@nestjs/authentication` глобальный.

## Безопасность

**Вход по подписи**
- Вызов одноразовый и живёт 5 минут. Он «сгорает» первой же попыткой (одна условная запись `UPDATE … WHERE used_at IS NULL`) — повтор и перебор невозможны, гонка параллельных попыток тоже.
- Подпись проверяется под **ровно теми байтами**, что выдал сервер (SHA-256 сообщения хранится в БД). Если кошелёк добавил инструкцию ComputeBudget — сообщение разбирается: тот же плательщик, тот же blockhash, ровно один memo с выданным текстом, других программ нет.
- Текст содержит домен фронтенда, адрес, сеть и срок — подпись для чужого сайта или чужого адреса не пройдёт.
- В транзакции второй обязательный подписант — случайный ключ без приватной части: подписанную транзакцию **невозможно отправить в сеть**, перехват не спишет даже комиссию.
- На любую ошибку проверки — один и тот же 401, без подсказок, что не так.

**Токены**
- Access — JWT HS256 (`typ: at+jwt`), 15 минут, проверяются подпись, `exp`, `iss`, `aud`; `alg: none` не принимается. Ключ — от 32 байт.
- Refresh — непрозрачный, одноразовый, хранится только SHA-256. Ротация при каждом обновлении; предъявление уже потраченного токена (его украли) отзывает всё семейство. Абсолютный срок семейства — 30 дней.
- Refresh живёт только в cookie `HttpOnly; SameSite=Strict; Path=/api/auth` (+ `Secure` и префикс `__Secure-` вне localhost): JavaScript и XSS его не прочитают, на остальной API он не уходит.
- Access-токен фронтенд держит в памяти, не в localStorage.

**CSRF и CORS**
- Cookie-эндпоинты требуют заголовок `X-Divra-Client: web` и `Origin`/`Sec-Fetch-Site` своего фронтенда. Простой кросс-сайтовый запрос этот заголовок не пришлёт, а preflight CORS разрешает только `APP_ORIGIN`.
- `verify` под тем же правилом — закрыт login CSRF.

**Прочее**
- Rate limit: 120/мин на IP везде, 10/мин на вход, не больше 5 живых вызовов на адрес. За прокси — `TRUST_PROXY`.
- Helmet (строгий CSP, HSTS, nosniff, запрет фреймов), тело запроса не больше 16 КБ, строгая валидация zod (лишние поля → 400).
- Конфигурация проверяется при старте; в production приложение не запустится с ключом из примера, без `Secure`-cookie или без https.
- Значения переменных не попадают в логи и ошибки.

## Тесты

```bash
npm test            # юнит
npm run test:e2e    # всё приложение на PGlite (PostgreSQL в процессе), своя база не нужна
```

e2e покрывают: регистрацию и вход, JWT-claims, подделку подписи, чужое сообщение, повтор вызова, просрочку, ротацию и кражу refresh-токена, выход, CSRF, CORS, валидацию, лимиты, заголовки. Хранилище refresh-токенов проходит официальный контракт `@nestjs/authentication/testing` с параллельными запросами.

## Чего пока нет

- Отзыв уже выданных access-токенов (живут до 15 минут — поэтому короткие).
- Удаление аккаунта (при нём нужно `TokenService.revokeAll()` — токены не связаны с users внешним ключом).
- Чистка таблицы `refresh_token_family_revocations` по сроку.

## Группы

- `groups` и `group_members`. Участник без `user_id` — pending: добавлен по имени, кошелька нет.
- Доступ — только участникам. Чужая, несуществующая группа и кривой id дают один и тот же 404:
  перебором не узнать, какие группы существуют.
- Имена: NFC, пробелы схлопнуты, без управляющих и bidi-символов (U+202E и т. п. переворачивают текст
  и годятся для подмены). В группе имена уникальны без учёта регистра (`lower(display_name)`).
- Лимиты: 100 групп на пользователя, 50 участников в группе. Проверяются под блокировкой строки
  пользователя / группы, поэтому параллельные запросы их не обходят.
- Имя создателя по умолчанию — короткий адрес (`Ccrt…KY47`), пока в профиле нет имени.
- Адрес участника для переводов — самый ранний Solana-кошелёк его аккаунта.

## Расходы и долги

- `expenses` и `expense_shares`. Суммы — целые центы доллара (`integer`), никаких дробей с плавающей точкой.
  API принимает доллары числом, но больше двух знаков после запятой — 400, а не тихое округление.
- Сумма долей обязана равняться сумме расхода до цента; участник в долях — не больше одного раза.
- Плательщик и доли — участники **этой** группы. Проверяет сервис (422), и дублирует база:
  составные внешние ключи `(group_id, member_id) → group_members(group_id, id)`.
- Исходная сумма и курс должны давать ту же сумму в долларах (±1 цент), иначе 400: нельзя показать
  в ленте «10 000 ₸», а записать $1000. Сам курс сервер пока не сверяет — появится вместе с `/rates`.
- Долги не хранятся, а считаются из расходов при каждом чтении (`src/groups/ledger.ts`):
  доли суммируются по парам «кто → кому» и зачитываются встречно. Нечему разойтись с расходами.
- Лента «Недавнее» — только расходы, изменившие твой баланс.

## Запросы на оплату

- Сумму запроса считает сервер — весь долг участника тебе после зачёта. Клиент только выбирает, у кого
  запросить; поле `amount` в теле — 400.
- Получатель (`recipient`) — только твой собственный кошелёк, иначе 422: запросом нельзя перенаправить
  чужой долг на посторонний адрес.
- Ссылка: `solana:<получатель>?amount=…&spl-token=<mint>&reference=<случайный ключ>` (Solana Pay).
  Divra деньги не держит — перевод идёт напрямую в кошельке.
- Код страницы — 16 случайных байт (base64url), страница открывается без входа и показывает только
  имена, группу, сумму и адрес получателя. Срок — 14 дней, потом 410.
- Оплату ищем в сети по `reference` (`getSignaturesForAddress` → `getTransaction`) и засчитываем, только
  если транзакция успешна и баланс нужного токена **у получателя** вырос не меньше чем на сумму.
  Записывается перевод «должник → ты», он гасит долг; в ленте — событие «перевод».
- Один действующий запрос на пару «кто просит → кто должен» (уникальный частичный индекс). Повторный
  запрос с той же суммой возвращает прежний; сумма изменилась — старый помечается `replaced_at`, его
  ссылка отвечает 410, а в «Отправленных» остаётся только новый. Перевод по старой ссылке, если всё же
  придёт, засчитывается.
- Одна транзакция засчитывается один раз (`payments.signature` уникальна), один запрос оплачивается
  один раз (блокировка строки + уникальный индекс).
- Когда ищем: при открытии страницы запроса (не чаще раза в 10 с) и в фоне каждые
  `PAYMENT_WATCH_INTERVAL_MS` (по 25 давно не проверенных). Сеть недоступна — запрос просто остаётся открытым.
- Оплата со страницы: расширения кошельков на компьютере не открывают ссылки `solana:`, поэтому
  бэкенд собирает перевод сам — `transferChecked` получателю (с созданием его токен-аккаунта, если нет)
  и `reference` как лишний read-only ключ, как в Solana Pay. От клиента — только адрес плательщика.
  Подписанную транзакцию бэкенд отправляет, только если в ней есть reference этого запроса и
  токен-аккаунт получателя (иначе 400 — не ретранслятор чужих транзакций). Засчитывает оплату всё равно
  поиск в сети. Оба эндпоинта — под `BrowserRequestGuard` и с лимитом.
- Фоновый поиск рассчитан на один процесс. Для нескольких реплик — advisory lock или отдельный воркер.

## Приглашения

- Код — 16 случайных байт (base64url), ссылка `APP_ORIGIN/join/<code>`, срок — 7 дней.
- Превью открывается без входа: название группы, кто пригласил, сколько участников, кого «заберёшь».
  Вступить можно только с подтверждённым кошельком (access-токен).
- Общая ссылка работает для любого числа людей до истечения (с лимитом 50 участников в группе).
  Имя по умолчанию — короткий адрес; занято — добавляется «2», «3».
- Персональная (на участника без кошелька) — один раз: вошедший становится этим участником вместе с
  его расходами и долгами. Ссылку можно создать только на участника этой группы без кошелька (иначе 409).
- Вход — одна транзакция с блокировками приглашения, группы и пользователя: одну персональную ссылку
  не заберут двое (второй — 410), лимиты не обойти параллельно. Уже состоишь в группе — `alreadyMember`.
- Отозвать ссылку пока нельзя — только дождаться срока. Общую ссылку стоит отправлять в доверенный чат.

## Рассчитаться

- Клиент выбирает только кому и сколько. Получатели, их адреса и предел суммы (не больше долга
  после зачёта) — с сервера. Получатель должен быть участником с кошельком; плательщик — твой кошелёк.
- Сервер собирает одну транзакцию: на каждого получателя — создание его токен-аккаунта (если нет)
  и `transferChecked`; в первом переводе — случайный `reference`. До 8 получателей, транзакция
  должна влезть в пакет Solana. Подписывает только плательщик. Срок — 2 минуты (blockhash).
- Отправка: подписанная транзакция принимается, только если в ней reference этого расчёта и
  токен-аккаунты всех получателей. Переход prepared → submitted атомарный — дважды не отправить.
- После отправки сервер ждёт подтверждения (до 30 с) и сверяет в сети балансы: засчитываются
  только переводы, где получатель действительно получил не меньше суммы. Не дождались — 503
  «отправлено, сеть подтверждает», и фоновая проверка досверит расчёт позже.
- Один перевод получателю засчитывается один раз: `payments (signature, to_member_id)` уникальна —
  транзакция не погасит долг и как расчёт, и как оплата по запросу.
- Балансы кошелька отдаются только для своих кошельков — эндпоинт не открытый прокси к RPC.
