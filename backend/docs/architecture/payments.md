# Оплата: запросы, оплата со страницы, «Рассчитаться»

Код: `src/payments/` (запросы, фоновый поиск), `src/payments/settlements/` («Рассчитаться», балансы),
`src/payments/solana/` (всё, что касается сети). Схема — `src/database/schema/payments.schema.ts`. Клиент —
[frontend/docs/architecture/payments.md](../../../frontend/docs/architecture/payments.md).

Главный принцип: **Divra не держит деньги и не верит клиенту на слово.** Переводы идут напрямую из кошелька в
кошелёк, а долг гасится только переводом, который сервер сам нашёл и проверил в сети.

## Запросить

```
POST /api/groups/:id/payment-requests { token, recipient, memberIds } → запросы со ссылками
GET  /api/groups/:id/payment-requests                                          → «Отправленные» (последние 50)
GET  /api/payment-requests/:code                                               → страница для плательщика (публично)
```

- Сумму считает сервер: весь долг участника тебе после зачёта. Поле `amount` в теле даёт 400.
- `recipient` — только твой собственный кошелёк, иначе 422: запросом нельзя перенаправить чужой долг.
- Ссылка Solana Pay: `solana:<получатель>?amount=…&spl-token=<mint>&reference=<случайный ключ>`.
- Код страницы — 16 случайных байт (base64url). Страница открывается без входа и показывает только имена,
  группу, сумму и адрес получателя. Срок — 14 дней, потом 410.
- Один действующий запрос на пару «кто просит → кто должен» (частичный уникальный индекс
  `payment_requests_active_uq`). Повтор с той же суммой возвращает прежний запрос. Если сумма изменилась, старый
  помечается `replaced_at`, его страница отвечает 410, а в «Отправленных» остаётся новый. Перевод по старой ссылке,
  если всё же придёт, засчитывается.
- Статусы в «Отправленных»: `open`, `paid` (с `signature`), `expired`.

### Отменить и напомнить

```
DELETE /api/groups/:id/payment-requests/:code          → 204
POST   /api/groups/:id/payment-requests/:code/remind   → { code, text, url, remindedAt, nextReminderAt }
```

- Оба — только для своего запроса (того, кто запрашивал). Чужой код — 404.
- **Отмена** ставит `cancelled_at` и `replaced_at`: запрос перестаёт быть действующим (тот же частичный индекс),
  страница отвечает 410 «Запрос отменён», в «Отправленных» его нет. Оплаченный отменить нельзя (409).
  Если перевод по старой ссылке всё же придёт, он засчитается — как у заменённого.
- **Напоминание**: сервер не рассылает сообщений, он отдаёт готовый текст со ссылкой, а пользователь
  отправляет его сам. `last_reminded_at` обновляется одним условным `UPDATE` — не чаще раза в сутки
  (`REMIND_INTERVAL_MS`), иначе 429. Оплаченный, отменённый или истёкший — 409.
- В «Отправленных» у запроса есть `remindedAt`.

## Вернули наличными

```
POST /api/groups/:id/cash-payments { memberId, amount } → { memberId, amount, remaining }
```

- Записывает **получатель**: `memberId` — тот, кто вернул, а должен он тому, кто спрашивает. Должник сам
  себе долг не закроет — у него нет долга «мне» перед получателем, ответ 409.
- Сумма не больше долга после зачёта (422), долг проверяется под блокировкой группы.
- В `payments` пишется строка `method = 'cash'`, без `signature` и `token`, с `recorded_by`. Журнал долгов
  учитывает её так же, как перевод в сети.
- Открытый запрос этой пары закрывается: сумма покрывает запрос — он **оплачен** этой записью
  (`payments.request_id`, `paid_at`; страница покажет «Оплачено» без подписи), частично — **отменён**.
- В ленте «Недавнее» — событие `type: 'cash'`.

## Как засчитывается оплата

1. По `reference` ищутся подписи (`getSignaturesForAddress`), затем транзакции (`getTransaction`, jsonParsed).
2. Транзакция должна быть успешной, а баланс нужного токена **у владельца-получателя** (разница pre/post token
   balances) должен вырасти не меньше чем на сумму.
3. В `payments` записывается перевод «должник → получатель» с `signature`. Он входит в журнал долгов как обратный
   долг ([groups-and-expenses.md](groups-and-expenses.md)), а в ленте показывается событием «перевод».
4. Один запрос оплачивается один раз (блокировка строки и уникальный индекс). Один перевод получателю засчитывается
   один раз: `payments (signature, to_member_id)` уникальна.

Когда ищем: при открытии страницы запроса (не чаще раза в 10 с, `RECHECK_MS`) и в фоне каждые
`PAYMENT_WATCH_INTERVAL_MS` (`payment-watcher.ts`, до 25 давно не проверенных запросов за проход, плюс досверка
отправленных расчётов). Если сеть недоступна, запрос просто остаётся открытым. `0` выключает таймер (так в e2e).
Фоновый поиск рассчитан на один процесс; для нескольких реплик нужен advisory lock или отдельный воркер.

## Оплата со страницы

Расширения кошельков на компьютере не открывают ссылки `solana:`, поэтому есть второй путь:

```
POST /api/payment-requests/:code/transaction { account }            → { transaction (base64) }
POST /api/payment-requests/:code/submit      { signedTransaction }  → { signature }
```

- Бэкенд собирает перевод сам; от клиента приходит только адрес плательщика.
- Подписанную транзакцию бэкенд отправляет, только если в ней есть `reference` этого запроса и токен-аккаунт
  получателя, иначе 400: эндпоинт не ретранслятор чужих транзакций.
- Засчитывает оплату всё равно поиск в сети, как выше.
- Оба эндпоинта публичные, но под `BrowserRequestGuard` и с лимитом.

## Рассчитаться

```
POST /api/groups/:id/settlements { token, payer, transfers: [{ memberId, amount }] } → { id, transaction, … }
POST /api/groups/:id/settlements/:sid/submit { signedTransaction }                            → итог по переводам
GET  /api/wallets/:address/balances                                                           → балансы своего кошелька
```

- Клиент выбирает только кому и сколько. Получатели, их адреса и предел суммы (не больше долга после зачёта)
  берутся с сервера. Получатель — участник с кошельком; плательщик — твой кошелёк.
- Одна транзакция: на каждого получателя — создание токен-аккаунта (если нет) и `transferChecked`; `reference` —
  в первом переводе. Не больше `MAX_SETTLEMENT_TRANSFERS = 8` получателей, транзакция должна влезть в пакет
  Solana. Срок — 2 минуты (время жизни blockhash).
- Статусы `settlements`: `prepared → submitted → confirmed | failed`. Переход `prepared → submitted` атомарный
  (`UPDATE … WHERE status`), поэтому дважды отправить нельзя.
- Отправка принимается, только если в транзакции есть `reference` этого расчёта и токен-аккаунты всех получателей.
- После отправки сервер ждёт подтверждения (`SETTLEMENT_TIMING`: 30 попыток по 1 с) и сверяет балансы.
  Засчитываются только переводы, где получатель действительно получил не меньше суммы. Если подтверждения нет,
  ответ — 503 «отправлено, сеть подтверждает», и фоновая проверка досверит расчёт позже.
- Балансы отдаются только для своих кошельков: эндпоинт не открытый прокси к RPC.

- Работы фонового поиска в нескольких репликах.
