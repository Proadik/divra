# Переводы мимо Divra и события для фронтенда

Код: `src/transfers/` (поток, сопоставление, API), `src/events/` (шина событий, WebSocket-шлюз).
Клиент — [frontend/docs/architecture/payments.md](../../../frontend/docs/architecture/payments.md#переводы-мимо-divra)
и [frontend/docs/architecture/state-and-data.md](../../../frontend/docs/architecture/state-and-data.md#события-с-сервера).

## Зачем

Тимур должен Адилю 32 USDC и переводит 30 USDC прямо из Phantom, без ссылки Divra. Divra замечает перевод
в сети и предлагает Адилю: «Тимур перевёл тебе 30 USDC — засчитать в „Бурабай"?». Засчитывает только
получатель: перевод проверен в сети, но за что он — знает только тот, кто получил деньги.

## Поток LaserStream (gRPC Helius)

```
TransferWatcher ── watch(ATA участников) ──▶ TransferStream (LaserstreamTransferStream)
        ▲                                             │ успешные транзакции с этими аккаунтами
        │ membership.changed                          ▼
   DomainEvents ◀── transfer.detected ── TransfersService.handle(tx) ──▶ detected_transfers
```

- **Подписка** — одна, фильтр `transactions.accountInclude` = токен-аккаунты (ATA) USDC/USDT пользователей,
  которые не выключили функцию (`users.detect_transfers`) и состоят в группе, где есть ещё хотя бы один участник
  с кошельком. Слушаем ATA, а не кошельки: при SPL-переводе адрес кошелька получателя в транзакцию не попадает.
  `vote: false`, `failed: false`, commitment `confirmed`.
- **Пересборка набора** — по событию `membership.changed` (вступил, вышел, удалил аккаунт, поменял настройку),
  с задержкой 1 с, новым запросом в том же потоке (`StreamHandle.write`), без переподключения. Пустой набор —
  поток закрывается: пустой `accountInclude` означает «все транзакции сети».
- **Надёжность** — переподключение и повтор пропущенного SDK делает сам (`replay: true`). Последний обработанный
  слот хранится в `chain_stream_state`, после перезапуска поток догоняет с него (окно повтора Helius — около
  48 часов). Без `HELIUS_API_KEY` поток выключен (`DisabledTransferStream`), остальное приложение работает.
- **Один процесс.** Как и фоновый поиск оплат, поток должен держать одна реплика (advisory lock или воркер).

## Сопоставление (`TransfersService.handle`)

1. Изменения балансов токенов по владельцам: `postTokenBalances − preTokenBalances` (`balanceChanges`).
   Берутся только USDC/USDT этой сети.
2. Есть получатель (баланс вырос) и отправитель (уменьшился) — оба пользователи Divra; у получателя функция включена.
3. В транзакции нет `reference` нашего запроса или расчёта — иначе её засчитает основной механизм.
4. Отправитель сейчас должен получателю хотя бы в одной общей группе (журнал долгов после зачёта).
5. Подсказка записывается в `detected_transfers` (уникально по `(signature, to_address)` — повтор из потока
   ничего не меняет), получателю уходит событие `transfer.detected`.

## API

```
GET  /api/me/detected-transfers               → подсказки за 30 дней, где отправитель ещё должен
POST /api/detected-transfers/:id/apply { groupId } → { groupId, amount, remaining }
POST /api/detected-transfers/:id/dismiss      → 204 («это не за долг»)
```

- В списке у каждой подсказки — группы, где отправитель сейчас должен (по убыванию долга). Долга больше
  нет — подсказка не показывается.
- **Засчитать** не верит потоку на слово: транзакция заново читается через RPC (`PaymentLookup.receivedBy`) —
  получатель должен был получить не меньше суммы, отправитель — потерять. Не подтверждена или не совпадает — 409. Дальше под блокировками подсказки и группы: долг пересчитывается, засчитывается `min(перевод, долг)`,
  в `payments` пишется обычный перевод `onchain` с подписью. Уникальность `(signature, to_member_id)`
  не даст засчитать его ещё раз (в том числе если та же транзакция уже оплатила запрос — 409).
  Открытый запрос пары закрывается: покрыт — оплачен, частично — отменён.
- Чужая подсказка — 404. Подсказки и настройка — только у получателя.
- Настройка — `PATCH /api/me { detectTransfers }`, по умолчанию включена.

## История переводов

```
GET /api/me/history?cursor=<курсор>&limit=20   → { items, nextCursor }
```

- **Индекс.** Каждая транзакция из потока, где отправитель или получатель — пользователь Divra, записывается
  в `chain_transfers`: строка на каждого получателя (у расчёта их несколько), отправитель — тот, у кого
  ушло больше всего этого токена. Повтор транзакции ничего не дублирует (`signature, to_address, mint`).
  Пишутся все такие переводы — в том числе по запросам и расчётам Divra и не связанные с долгами.
- **Второй источник** — засчитанные оплаты в сети (`payments`, `method = 'onchain'`): так в истории есть оплаты,
  сделанные, пока потока не было (нет ключа, простой). Если транзакция уже есть в индексе, вторая строка
  не показывается.
- **Элемент:** сумма, токен, направление (`in` — пришло тебе, `out` — ушло), другая сторона (имя в общей группе,
  если есть, и адрес, если известен), где засчитан (`countedIn` — название группы), ждёт ли решения
  (`suggested`), подпись для Solscan.
- **Пагинация** — курсор `(created_at, id)`, новые сверху; `limit` 1–50 (по умолчанию 20), на одну запись больше —
  чтобы знать, есть ли следующая страница. Курсор хранит время с микросекундами Postgres (`created_at::text`):
  иначе на границе страницы строка могла бы повториться. В отличие от `offset`, новые переводы не сдвигают
  страницы — нет пропусков и повторов при бесконечной прокрутке.
- Новые строки индекса — событие `history.changed` обоим участникам.

## События для фронтенда (WebSocket)

- **Шина** `DomainEvents` (`src/events/domain-events.ts`) — внутри процесса. Сервисы сообщают о том, что
  изменилось: `group.changed { groupId }` (расходы, участники, переводы, запросы, наличные, расчёты),
  `membership.changed`, `transfer.detected { userId, id }`.
- **Шлюз** `EventsGateway` — socket.io на `/api/socket.io`, только транспорт WebSocket (не нужны sticky-сессии).
  - Вход: access-токен в handshake `auth.token` (не в URL — URL попадает в логи), проверка подписи, `iss`, `aud`,
    `typ` и того, что пользователь существует. Отказ — событие `unauthorized` и разрыв, причина не сообщается.
  - Соединение закрывается, когда токен истекает; клиент обновляет токен и переподключается.
  - `Origin` проверяется для каждого подключения (`DivraIoAdapter.allowRequest`): CORS не защищает WebSocket,
    без этой проверки чужой сайт мог бы открыть соединение (cross-site WebSocket hijacking).
  - Клиент только слушает: обработчиков сообщений нет, буфер — 4 КБ.
  - Пользователь — в комнате `user:<id>`. `group.changed` уходит всем действующим участникам группы с кошельком,
    `transfer.detected` — только получателю, `history.changed` — отправителю и получателю перевода.
- **События тонкие** — только «что изменилось». Данные клиент перечитывает обычными запросами, где работают
  все проверки доступа и схемы.
- **Прокси.** Vite и nginx должны пропускать WebSocket на `/api` (`ws: true`; в nginx — `Upgrade`/`Connection`).

## Лог

- После каждой пересборки подписки — список кошельков, которые слушаем, и их токен-аккаунты.
- Каждая транзакция из потока с переводом стейблкоина — строка `Перевод (слот …): USDC 12.5: A → B`.
- Если в переводе есть пользователь Divra, но подсказки нет, — причина: не пользователь, выключена
  настройка, отправитель не должен получателю, перевод по ссылке Divra.
- `TRANSFER_LOG_ALL=true` (только devnet) — в фильтр добавляются сами mint USDC/USDT, и в лог попадают все их
  переводы в сети. Так видно, что поток вообще работает. Ловятся переводы через `transferChecked` (так переводят
  Phantom и Solflare): в простом `transfer` аккаунта mint в транзакции нет.

## Проверка на devnet

1. Ключ Helius (план Developer и выше для devnet) — в `.env`: `HELIUS_API_KEY`, а `SOLANA_RPC_URL` — тот же Helius RPC.
2. Два аккаунта в одной группе, один должен другому.
3. Из Phantom (devnet) переводим USDC напрямую. В логе бэкенда — `Замечен перевод … → подсказка …`,
   у получателя на главной появляется карточка без перезагрузки.
