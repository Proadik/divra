# Подтверждение владения кошельком

Подключить кошелёк недостаточно: адрес может подставить кто угодно. Поэтому вторым шагом
пользователь подписывает транзакцию, которую выдал бэкенд, и только после проверки подписи
получает сессию и попадает на главную.

## Последовательность

```
Пользователь      Frontend                    Кошелёк              Backend
    │  выбирает кошелёк  │                          │                      │
    │──────────────────▶ │ adapter.connect()        │                      │
    │                    │─────────────────────────▶│ окно «Подключить»    │
    │                    │◀──────── адрес ──────────│                      │
    │                    │ status = connected → /verify                    │
    │                    │ POST /auth/wallet/challenge {chain, address}    │
    │                    │────────────────────────────────────────────────▶│ nonce, memo-tx
    │                    │◀──── {challengeId, transaction, message} ───────│
    │  «Подписать»       │ adapter.sign(transaction)│                      │
    │──────────────────▶ │─────────────────────────▶│ окно «Подписать»     │
    │                    │◀──── signedTransaction ──│                      │
    │                    │ POST /auth/wallet/verify {challengeId, signedPayload}
    │                    │────────────────────────────────────────────────▶│ проверка
    │                    │◀────────────── {sessionToken} ──────────────────│
    │                    │ status = verified → /                           │
```

## Что подписывает пользователь (Solana)

Транзакция v0 с одной инструкцией Memo:

```
Divra: подтверждение владения кошельком
Адрес: <адрес>
Nonce: <16 hex>
Выдано: <ISO-время>
Транзакция не отправляется в сеть и ничего не списывает.
```

Fee payer — сам пользователь, blockhash — свежий из RPC. Транзакция **никогда не отправляется в сеть**:
она используется только как контейнер для подписи. Такой способ выбран вместо `signMessage`, потому что
подписывать транзакции умеют все кошельки, включая аппаратные, а подпись произвольных сообщений
поддерживается не везде (например, Ledger при работе через расширение).

Текст memo показывается пользователю на экране `/verify` до подписи.

## Контракт API

Схемы — `src/shared/api/auth/schemas.ts` (zod). Ответ сервера проверяется схемой: если он не совпал
с контрактом, запрос считается ошибкой.

`POST /auth/wallet/challenge`

```json
{ "chain": "solana", "address": "<base58>" }
```

```json
{
  "chain": "solana",
  "challengeId": "…",
  "transaction": "<base64, wire format, без подписей>",
  "message": "<текст memo>",
  "expiresAt": "2026-11-16T18:09:34.861Z"
}
```

Ответ размечен по `chain`: другие сети добавят свой вариант (например, `ethereum` → `typedData`).

`POST /auth/wallet/verify`

```json
{ "challengeId": "…", "chain": "solana", "address": "<base58>", "signedPayload": "<base64>" }
```

```json
{
  "tokenType": "Bearer",
  "accessToken": "<JWT HS256, typ at+jwt, 15 минут>",
  "expiresIn": 900,
  "user": { "id": "<uuid>", "chain": "solana", "address": "<base58>", "created": true }
}
```

Вместе с ответом сервер ставит refresh-cookie `divra_rt` (в проде `__Secure-divra_rt`):
HttpOnly, SameSite=Strict, Path=/api/auth. Из JS она не читается.

`POST /auth/refresh` — без тела, по cookie. Возвращает новый access-токен и новую cookie.
Refresh-токен одноразовый: повторное использование старого отзывает всю цепочку (кража).

`POST /auth/sign-out` — отзывает refresh-токен и стирает cookie. `GET /me` — профиль (Bearer).

Все запросы к `/auth/*` идут с заголовком `X-Divra-Client: web`. Без него, с чужим `Origin` или
`Sec-Fetch-Site: cross-site` бэкенд отвечает 403 — защита от CSRF поверх SameSite.

## Что проверяет бэкенд

Реализация — `backend/src/auth` (подробности в `backend/README.md`).

1. Вызов гасится **атомарно до проверки подписи** (`UPDATE … WHERE used_at IS NULL AND expires_at > now()`):
   повтор и гонка двух запросов невозможны. TTL 5 минут, не больше 5 активных вызовов на адрес.
2. Адрес совпадает с тем, для которого выдан вызов.
3. Подпись ed25519 этого адреса валидна для **точных байтов** выданного сообщения (сравнение по SHA-256).
   Кошелёк может добавить только инструкции ComputeBudget — любое другое изменение отклоняется.
4. В транзакции второй подписант — случайный ключ, который сервер выбрасывает: отправить её в сеть нельзя.
5. Любая ошибка проверки — один и тот же 401 без подробностей.

Мок (`src/shared/api/mock/auth.ts`) повторяет контракт в браузере. Включается `VITE_AUTH_MOCK=true`
(пусто — как `VITE_API_MOCK`) и грузится отдельным чанком, в сборку с настоящим API не попадает.
Вход можно сделать настоящим, а остальные данные оставить в моке: `VITE_AUTH_MOCK=false`, `VITE_API_MOCK=true`.

## Frontend

- `features/wallet-auth/model/use-verify-wallet.ts`
  - `useQuery` за вызовом: `staleTime: Infinity`, `gcTime: 0` — вызов одноразовый.
  - `useMutation`: подписать → отправить → `verified(accessToken)`.
  - После любой ошибки вызов перезапрашивается (старый nonce уже сгорел).
- Шаги на экране (`TxSteps`): сервер готовит транзакцию → подпись в кошельке → проверка подписи.
- Access-токен живёт **только в памяти** (`entities/wallet`, стор сессии). В localStorage — лишь флаг
  `signedIn`, адрес и id кошелька. XSS не может унести долгоживущий секрет.
- `shared/api/client.ts` добавляет `Authorization: Bearer`, `credentials: 'include'` и `X-Divra-Client`.
  На 401 один раз обновляет токен и повторяет запрос; не вышло — `sessionExpired()`, экран `/verify`.
- После перезагрузки `useWalletSessionSync` получает новый токен через `/auth/refresh`.
- Refresh одноразовый, поэтому вкладки обновляют токен по очереди: `navigator.locks` (`divra.auth-refresh`).
- Мост между стором и клиентом — `app/state/auth-bridge.ts` (`configureAuth`), shared не знает про entities.
- В dev Vite проксирует `/api` на `VITE_API_PROXY_TARGET` (по умолчанию `http://localhost:3000`):
  один origin, cookie SameSite=Strict работает без CORS.

## Профиль и удаление аккаунта (`pages/settings`)

- **Имя профиля** — `PATCH /me { displayName }` (`ProfileNameForm`). Им входишь в новые группы; в старых
  бэкенд заменяет имя по умолчанию (короткий адрес или прежнее имя профиля). Имя, которое тебе
  дали вручную в какой-то группе, не меняется.
- **Удалить аккаунт** — `DELETE /me` (`features/wallet-auth`: `DeleteAccountButton`, `useDeleteAccount`).
  Бэкенд удаляет кошельки, отзывает все refresh-токены и стирает cookie; запрос — с `X-Divra-Client`.
  Фронт после этого сбрасывает сессию, весь кэш и отключает кошелёк. В группах ты остаёшься
  участником без кошелька с тем же именем: расходы и долги друзей не пропадают. Войти тем же
  кошельком можно снова, но это новый аккаунт без групп.

## Ограничения текущей версии

- Access-токен нельзя отозвать до истечения (15 минут): выход отзывает refresh-цепочку, а не JWT.
- Подпись тестировалась фейковым кошельком (Wallet Standard). Как Phantom/Solflare подписывают
  транзакцию со вторым (чужим) подписантом, нужно проверить на живом кошельке.
